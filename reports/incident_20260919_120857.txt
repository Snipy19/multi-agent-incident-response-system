### 1. Summary  
During the afternoon of 19 Sep 2026, the checkout service experienced a cascade of performance issues: a 30‑second database connection timeout, host memory utilization at ~95 %, and noticeably sluggish disk I/O. The combination of these metrics triggered an anomaly alert. The service became intermittently unavailable to end‑users, causing a temporary degradation of the checkout flow.

---

### 2. Root Cause  
High memory consumption (~95 %) induced severe memory pressure on the host. This led to frequent garbage‑collection pauses and triggered swapping, which in turn slowed disk I/O. The degraded I/O and increased GC latency reduced the checkout service’s ability to acquire database connections from its pool, resulting in the observed timeouts. The slow disk I/O is a secondary effect of the memory pressure, not the primary trigger.

**Root‑cause confidence:** 0.88 (high)

---

### 3. Recommended Fix  
1. **Increase JVM heap** – raise `-Xmx` for `checkout-service` to **4 GB** and enable **G1GC** to reduce pause times.  
2. **Add host memory** – provision an additional **8 GB of RAM** to eliminate swapping.  
3. **Adjust connection pool** – scale the pool size to align with the new memory capacity.  
4. **Monitoring** – instrument memory usage with JMX or Prometheus; set alerts for >80 % usage and GC pause >200 ms.

Implementing these changes should restore stable database connectivity and eliminate the memory‑induced I/O bottleneck.

**Fix confidence:** 0.90 (very high)
