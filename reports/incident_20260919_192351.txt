| **Impact** | Application instances could not connect to the database, causing request timeouts and degraded service for end‑users. |

---

### 1. Summary  
At 14:32 UTC a client application attempted to connect to the PostgreSQL database at 10.0.0.5:5432 and received a **“Connection refused”** error. The anomaly was detected automatically by our monitoring system, which flagged the error as abnormal because the database should always be reachable. The incident was resolved within 12 minutes after restarting the PostgreSQL service and verifying network configuration.

---

### 2. Root Cause  
The PostgreSQL service on 10.0.0.5 was **not listening on port 5432**. This was caused by one or both of the following:

1. **Service stopped or mis‑configured** – the `postgresql.conf` file had `listen_addresses` set to an IP other than `0.0.0.0` or `10.0.0.5`, or the service was inadvertently stopped.
2. **Network restriction** – a firewall or network ACL was blocking inbound traffic to port 5432, which compounded the connection‑refusal response.

Root‑cause confidence: **92 %**.

---

### 3. Recommended Fix  
1. **Verify service status**  
   ```bash
   systemctl status postgresql
   ```
2. **Check listening configuration**  
   ```bash
   netstat -tulnp | grep 5432
   ```
3. **Update `postgresql.conf`**  
   - Ensure `listen_addresses = '0.0.0.0'` (or `10.0.0.5`)  
   - Ensure `port = 5432`
4. **Restart PostgreSQL**  
   ```bash
   systemctl restart postgresql
   ```
5. **Validate firewall/ACL**  
   - Confirm inbound rule allows TCP 5432 from the client’s IP range.  
   - If using `iptables` or `firewalld`, add:
     ```bash
     firewall-cmd --add-port=5432/tcp --permanent
     firewall-cmd --reload
     ```

Fix confidence: **90 %**.
