**Incident Post‑Mortem – Checkout Service Outage**  
*Date: 2026‑09‑19*  

---

### 1. Summary  
At 14:32 UTC the checkout‑service host reported a critical failure. The host experienced:  

- Database connection timeouts (30 s)  
- Memory usage at ~96 %  
- Disk‑I/O latency spikes to 800 ms  
- 12 % packet loss on eth0  
- 15 authentication failures for the `db‑reader` account in the last 2 min  

The combination of these symptoms caused a cascading outage that rendered the checkout service unavailable to users.

---

### 2. Root Cause  
The outage was triggered by **cumulative memory pressure** on the host:

1. **High memory usage (~96 %)** caused frequent garbage‑collection pauses and forced the JVM to swap.  
2. **Swapping** increased disk‑I/O latency to 800 ms, creating a bottleneck.  
3. The I/O bottleneck, together with **12 % packet loss on eth0**, degraded authentication attempts for the `db‑reader` account.  
4. These failures cascaded into **database connection timeouts** and overall service instability.  

*Primary root cause:* Memory exhaustion.  
*Secondary contributing factors:* Disk‑I/O latency, network packet loss, authentication failures.

Confidence in this analysis: **92 %**.

---

### 3. Recommended Fix  
1. **Add 4 GB of physical RAM** to the host.  
2. **Reduce JVM heap** to 2 GB and enable **G1 GC**.  
3. **Configure a memory‑usage alert** (threshold 90 %) to trigger proactive remediation.  
4. **Monitor GC and memory metrics** to confirm that GC pauses and swapping are eliminated.  

These actions will lower GC pauses, reduce disk‑I/O latency, eliminate packet loss, and stop authentication failures and DB timeouts.

Confidence in the fix: **90 %**.
